## Part 1 — Repo Structure

The layout below is a monorepo. The three new directories — `specs/`, `graph/`, and `behavior-index/` — are the artifacts this architecture introduces on top of normal code. Everything else is familiar.

```
my-saas/
├── AGENTS.md                        # Agent entry point: how to build, test, navigate
│
├── specs/                           # Intent layer — authoritative behavioral source
│   ├── invoicing/
│   │   ├── create_invoice.yaml
│   │   └── void_invoice.yaml
│   ├── auth/
│   │   └── token_validation.yaml
│   └── _schema.yaml                 # Shared spec schema (inputs / invariants / effects)
│
├── graph/                           # Compiled spec graph — generated, versioned, diffable
│   ├── nodes/
│   │   └── create_invoice.json      # Graph node: requires, produces, affects
│   ├── edges.json                   # Dependency + propagation edges
│   └── graph.json                   # Full materialized graph
│
├── behavior-index/                  # Spec ↔ code mapping — generated by CI
│   ├── create_invoice.json          # { spec, impl: [...], routes: [...] }
│   └── index.json                   # Full cross-reference index
│
├── docs/
│   ├── architecture/
│   ├── flows/                       # Per-flow: README, sequence.mmd, runbook.md
│   └── components/                  # Per-service: interfaces, data-model, runtime
│
├── services/
│   ├── invoicing/
│   └── auth/
│
├── .github/
│   └── workflows/
│       ├── spec-compile.yml         # On spec PR: compile graph, update index
│       ├── impact-analysis.yml      # On code PR: traverse graph → scope tests
│       └── spec-verify.yml          # On code PR: validate impl against spec
│
└── scripts/
    ├── compile-spec-graph.ts        # specs/ → graph/
    ├── build-behavior-index.ts      # graph/ + src/ → behavior-index/
    └── impact-analysis.ts           # Changed files → affected spec nodes → test scope
```

**Key conventions:**

- `specs/` files are authored by engineers and PMs. They gate feature PRs — no spec, no implementation PR.
- `graph/` and `behavior-index/` are **generated** by CI, committed back, and diffed in PRs so impact is visible in review.
- `AGENTS.md` is the agent entry point — tells coding agents where to look, how to validate, and what not to touch. This follows the [progressive disclosure](../../../techniques/progressive-disclosure.md) pattern: a small entry point pointing into structured directories.
- The `docs/` directory follows the [codebase cartography](../../../techniques/codebase-cartography.md) convention: `components/` for what the pieces are, `flows/` for how they relate.

**Polyrepo variant:** In a polyrepo organization, each service maintains its own `specs/` directory with local spec compilation. A separate "platform" repository aggregates cross-service edges into a unified graph and runs cross-service impact analysis. The behavioral index spans repositories through a shared registry. The architecture is the same; the compilation boundary shifts from directory to repository.

### Spec File Format

```yaml
# specs/invoicing/create_invoice.yaml

# ── Human-authored ──────────────────────────────────────────────────────────
goal: enable billing team to create invoices without manual data-entry errors
  # Name the goal, not the solution. Goals survive implementation changes; solutions don't.

constraints:
  frozen: [invoice_schema_v2, payment-service HTTP API]
  limits: [no new database tables]
  # State these before any agent starts. Late-discovered constraints are the
  # leading cause of scope drift.

# ── Agent-seeded (spec-seed skill, from codebase analysis) ──────────────────
feature: create_invoice
domain: invoicing

success_criteria:
  - invoice creation error rate < 2% measured over first 30 days post-deploy
  - end-to-end latency < 500ms at p95 under normal load
  # Define done measurably. A measurable criterion is worth a hundred vague requirements.

inputs:
  - authenticated_user
  - invoice_items[]

invariants:
  - total == sum(item.amount for item in invoice_items)
  - invoice_items is non-empty

effects:
  - invoice_persisted
  - invoice_created_event emitted

scenarios:
  - given: valid user with 3 line items
    when: POST /api/invoices
    then: 201 + invoice_created_event on queue

  - given: empty line items
    when: POST /api/invoices
    then: 422 Unprocessable

tasks:
  - [ ] implement POST /api/invoices handler
  - [ ] add invariant validation (empty items, total check)
  - [ ] emit invoice_created_event on successful persist
  # Agent checks off items as it works; verifies against success_criteria before surfacing for review.

decisions:
  - context: invoice_schema_v2 is frozen per billing-service contract
    decision: validate against existing schema; no new fields
    consequences: no new columns needed; constrains the input model
  # Record decisions as they're made. An undocumented decision is an ambiguity
  # waiting to cause a merge conflict.
```

The human authors `goal` and `constraints`; the `spec-seed` skill seeds the rest from codebase analysis; the human then reviews and edits before any implementation begins. After the checkpoint, the agent maintains `tasks` and `decisions` as it works. At any given moment the spec reads like a cross between an RFC, an ADR, and a project tracker — which is more or less exactly what it is.

This single file serves as instruction to the agent, acceptance criteria for CI, and behavioral documentation for engineers — applying [specification discipline](../../../techniques/specification-discipline.md) to produce artifacts that satisfy the self-check heuristic: the agent knows where to start, what to implement, and what proves completion. The [spec authoring workflow](spec-authoring.md) describes the full seeding process, including how `decisions:` gets populated from constraint elicitation rather than written after the fact.

## Part 2 — 90-Day Pilot

**Domain:** Pick one bounded domain — billing or invoicing is ideal. High business value, existing tests to compare against, and a clear event boundary (`invoice_created_event`) that makes graph edges visible.

**Goal:** Reach [Stage 2](adoption-roadmap.md) of the adoption roadmap (executable specs + verification) with the graph infrastructure already in place for Stage 3. In [Agent Readiness Model](../maturity-model.md) terms, this targets L2–L3 across the Task Discovery, Documentation, and Testing pillars.

### Phase 1 — Weeks 1–4: Spec Authoring and Compilation

**Goal:** Write 8–12 specs for existing features. Compile them into a graph. Commit it.

For the discipline behind writing specs that are complete and grounded in system context before the first commit, see [Spec Authoring Workflow](spec-authoring.md). The `spec-seed` skill from the spec-authoring plugin automates Stage 3 of that workflow: the engineer authors `goal` and `constraints`; the skill seeds `inputs`, `invariants`, `effects`, `scenarios`, `success_criteria`, and `tasks` from codebase analysis.

You are not building new features — you are describing what already exists. This forces clarity about what the system actually does. (A practical question that arises immediately: how granular should each spec be? A useful heuristic — each spec should deliver independently testable value. If a feature has sub-capabilities that different roles own or that could ship independently, split them. If the behaviors are interdependent and only make sense together, keep them in one spec.)

```typescript
// scripts/compile-spec-graph.ts
import { parse } from "yaml";
import { readFileSync, writeFileSync } from "fs";
import { glob } from "glob";

const specFiles = glob.sync("specs/**/*.yaml");

const nodes = specFiles.map(file => {
  const spec = parse(readFileSync(file, "utf8"));
  return {
    id: spec.feature,
    domain: spec.domain,
    inputs: spec.inputs,
    effects: spec.effects,
    invariants: spec.invariants,
  };
});

// Build edges: if spec A's effect matches spec B's input, connect them
const edges: { from: string; to: string; via: string[] }[] = [];
for (const a of nodes) {
  for (const b of nodes) {
    const shared = a.effects?.filter((e: string) => b.inputs?.includes(e));
    if (shared?.length) {
      edges.push({ from: a.id, to: b.id, via: shared });
    }
  }
}

writeFileSync("graph/graph.json", JSON.stringify({ nodes, edges }, null, 2));
```

**Milestone:** Graph renders in CI. Engineers can see the invoicing domain as a connected behavioral model.

### Phase 2 — Weeks 5–10: Behavior Index and Impact Analysis

**Goal:** Code PRs automatically identify which specs they affect and which downstream behaviors are at risk.

```typescript
// scripts/impact-analysis.ts
// Called by CI with a list of changed files
import graph from "../graph/graph.json";
import index from "../behavior-index/index.json";

const changedFiles = process.argv.slice(2);

const affectedSpecs = index
  .filter((entry: { impl: string[]; spec: string }) =>
    entry.impl.some(file => changedFiles.includes(file))
  )
  .map((entry: { spec: string }) => entry.spec);

function downstream(specId: string, visited = new Set<string>()): string[] {
  if (visited.has(specId)) return [];
  visited.add(specId);
  const deps = graph.edges
    .filter(e => e.from === specId)
    .map(e => e.to);
  return [specId, ...deps.flatMap(d => downstream(d, visited))];
}

const impact = [...new Set(affectedSpecs.flatMap((s: string) => downstream(s)))];
console.log(JSON.stringify({ affectedSpecs, transitiveImpact: impact }));
```

The output drives two things in CI: scoping which test suites to run, and posting an impact summary as a PR comment.

**Example output for a change to `InvoiceService.create()`:**

```
{
  "affectedSpecs": ["create_invoice"],
  "transitiveImpact": ["create_invoice", "capture_payment", "ledger_update"]
}
```

**Milestone:** Behavioral impact is visible on every code PR without any manual analysis.

### Phase 3 — Weeks 11–13: Spec Verification Gate

**Goal:** PRs cannot merge if the implementation violates a spec invariant or fails a declared scenario.

```typescript
// scripts/verify-spec.ts
import { parse } from "yaml";
import { readFileSync } from "fs";

const specFile = process.argv[2];
const BASE_URL = process.env.TEST_BASE_URL!;
const TEST_TOKEN = process.env.TEST_TOKEN!;

const spec = parse(readFileSync(specFile, "utf8"));

for (const scenario of spec.scenarios) {
  const [method, path] = scenario.when.split(" ");
  const res = await fetch(`${BASE_URL}${path}`, {
    method,
    headers: { Authorization: `Bearer ${TEST_TOKEN}` },
    body: JSON.stringify(scenario.given),
  });

  const expectedStatus = parseInt(scenario.then.split(" ")[0]);
  if (res.status !== expectedStatus) {
    console.error(`FAIL [${spec.feature}] — ${scenario.given}`);
    console.error(`  expected: ${expectedStatus}, got: ${res.status}`);
    process.exit(1);
  }
  console.log(`PASS [${spec.feature}] — ${scenario.given}`);
}
```

The `spec-verify.yml` workflow runs this against every spec touched by the PR. Fail means no merge.

**Milestone:** You have a behavior-gated PR workflow running on real features. The [spec graph](../../../GLOSSARY.md#spec-graph) is the control plane.

## What Comes Next

The pilot delivers Stage 2 with graph infrastructure already in place. Stage 3 — graph-aware CI, AI agent navigation, and planning-layer integration — is a straight-line extension, not a rearchitecture. See the [Adoption Roadmap](adoption-roadmap.md) for the full progression.

| Stage | Builds On Pilot With |
|---|---|
| **Stage 3 — Behavioral Graph Platform** | Add planning engine; route agents through behavioral index; expand to additional domains |
| **Stage 4 — Agentic Development** | Connect intent layer to AI planner; close the feedback loop from runtime telemetry |

```
Pilot output
  → spec graph as behavioral model
  → behavior-index as navigation layer
  → CI as behavioral guardrail
      → Stage 3: graph-aware planning
          → Stage 4: intent → plan → implement → verify
```

The spec graph you build in 90 days becomes the foundation every subsequent stage compiles against.
